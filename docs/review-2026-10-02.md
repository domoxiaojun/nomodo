# Telegram Bot 专项审查与完善

日期：2026-10-02。基线：`9aa10e5`。目标为当前独立 Python/uv Bot；SimpRead 仅提供阅读、结构化文章和导出功能参考。无需迁移扩展 Manifest、Webpack 或浏览器插件体系，也不修改 ParseHub Worker。

## 本轮修复

| 问题 | 原行为及影响 | 本轮结果 |
| --- | --- | --- |
| 媒体租约被导出层过早释放 | Service 与 Telegram save 都在 finally 释放；保存失败后重试、另存目标会丢媒体 | 统一由待处理文章持有，过期或取消时释放，保存不再重复释放 |
| 长任务与过期清理竞争 | Notion 导出过程中可能被维护循环删除文章、释放媒体 | 同一用户有操作锁时继续续租并暂缓过期删除 |
| 取消跨聊天生效 | 用户在群组发 `/cancel` 可以中断私聊任务 | 活跃任务记录发起聊天，只接受同聊天取消 |
| Worker 异常响应漏清理 | GET 覆盖 job 后丢失原 id；空 results/无效 media 在 finally 再次异常 | 稳定保存创建时 job id，验证响应结构，安全清理已知租约并返回统一错误 |
| HTML 被纯文本覆盖 | 同时返回 plainContent/htmlContent 时失去标题、表格和列表结构 | Markdown 优先，其次 HTML，再使用纯文本；支持显式 HTML contentFormat |
| 容器内链接遗漏 | 标题、列表、引用、表格里的链接/图片没有独立提取 | 保留安全链接和媒体引用，既有嵌套列表展平边界不变 |
| 预览缺少列表/表格 | 仅取 Block.text，纯列表文章预览空白 | 按块渲染预览，包含 items/rows；仍仅预览摘要，文件保存完整正文 |
| 说明文字链接被忽略 | 只监听 text 消息 | 图片/视频等 caption 中的普通 URL 也进入原有预检与解析流程 |
| 资源权限不足被当成登录失效 | Notion 403 清除用户所有本地 Notion 授权及目标 | 401 才表示授权失效；403 保留配置并提示检查资源共享 |
| LLM 脱敏误删正文 | JSON 转义换行后才执行按行脱敏，可能吞掉后续字段并破坏 JSON | 对每个原始文本字段、列表项、表格单元格脱敏后序列化，正常正文和原文对象保留 |

对应位置：`telegram/app.py`、`telegram/callbacks.py`、`worker/client.py`、`domain/normalize.py`、`domain/blocks.py`、`integrations/notion/client.py`、`integrations/notion/service.py`、`integrations/openai/client.py`。

## 架构判断

目前 `Worker → Article → Telegram/导出` 的边界适合 Bot；白名单、用户/聊天绑定、一次性写入确认、固定服务地址、未知写入隔离和凭据加密值得保留。本轮回归继续覆盖这些约束，不增加隐式 Notion 写入或由模型决定的网络访问。

优化应围绕信息保真、可靠重试和用户反馈，避免直接搬运 SimpRead 的页面 DOM、扩展权限与任意脚本插件。当前不需要新增本地数据库服务、另一个接收 updates 的 Bot 或重写 Worker。

## 后续优先级

### 第一阶段已落地

- 持久导出任务 ID、原文章快照、按任务确认恢复/重试；支持重启、文章过期和目标切换，保留旧幂等键及标记。旧无快照记录可列出，但不会凭最新文章猜测恢复。
- `/articles`、`/select` 与持久选择，按用户和聊天隔离；选中文章过期不静默切换。
- Notion 目标/文章/任务长列表按 Telegram UTF-16 长度分消息完整输出，优先按换行分段。
- 隐藏文字链接、caption 和回复原消息后 `/read`；多链接逐项进度。
- 完整目标检索成功后原子替换列表；分页游标缺失或重复时报错，避免无限循环或误删已有目标。
- 活跃请求使用独立任务管理，关闭时取消并等待清理；健康状态加入维护任务存活检查，异常日志只写异常类别。

以下未被本节列为完成的项目仍属后续工作。

### P1：生产验收和故障恢复

- 对真实 Worker、Telegram 文件发送、Notion OAuth/API 做端到端验收；必须分别核对解析完成、预览投递、租约续期、取消和外部写入结果。模拟测试不能代替这一步。
- Worker 创建请求如果服务端已接受、客户端却在拿到 job id 前断线，本地目前没有可持久恢复的请求记录。只读核对现有 Worker 源码后确认：相同 idempotencyKey 和请求指纹可以复用任务，过期任务会拒绝复活；未发现独立 requestId 查询路由。后续须持久保存请求并使用原键恢复，还要处理取消和 Worker 记录保留期限；本阶段不盲重试创建。
- Notion unknown 的持久任务列表及按任务恢复已完成；真实服务中的标记核对和上传文件时效仍需验收。
- Notion 内容哈希目前不包含 description。仅描述变化可能被当成同一导出；不能直接改变全量哈希算法，否则历史已发送记录失配并生成重复页面。后续应设计带版本的身份与 checkpoint 迁移。本轮不改历史幂等键。

### P2：完整性与交互

- 文章选择、完整长列表、隐藏文字链接、引用消息 `/read` 和多链接进度已完成；深层外部引用、不可见聊天历史不自动抓取。
- 嵌套列表、引用内代码、多媒体文件类型与行内样式仍可提升；建立网页固定样本，以完整语义保留为验收，不做逐像素复刻。
- Notion 已上传但尚未附加的文件存在时效边界，持久化 blocks 里的上传引用需要过期检测/重建策略；新增目标检索还应避免保留已经不可访问的陈旧目标。
- 维护任务存活健康状态、异常类别日志和主动关闭清理已完成；任务耗时指标、维护任务长时间卡住的检测仍可增加。

### P3：性能与新功能

- 当前解析信号量固定为 2，单篇媒体串行下载，维护循环也串行续租。先测多用户负载和 Worker 容量，再引入可配置并发与公平调度，避免用截断正文或减少文章数掩盖慢请求。
- EPUB、PDF、分享卡和稍后读交互可以借鉴 SimpRead。优先实现基于 Article 的可测试导出器；Web App 放在消息流程稳定之后。
- LLM 的用户模型配置、预算预留和派生结果可进一步做清晰反馈；维持原文不变、费用透明和明确写入确认。

## 验证方式和边界

回归使用项目现有 `.venv` 和 `uv run --no-sync`：pytest、Ruff、mypy。新增场景覆盖异构 Worker 响应、异常清理、导出失败/成功后租约保留、过期与活跃任务、跨聊天取消、caption、富文本与脱敏保真；其余原有安全和导出幂等测试继续执行。

测试只使用临时 SQLite 文件、模拟 HTTP/Telegram 对象，不安装数据库服务，不运行 Docker，不调用真实账户。未修改依赖、部署配置或 ParseHub 仓库。最终命令结果记入根目录 `plan.md`。
